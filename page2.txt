## Building a module

The rules that let many teams share one app without breaking each other's work.

Module boundaries

- Don't write to global state, add global CSS, or patch the shell.
- Talk to the shell and other modules through \[events / shared store / router API\] only.
- Get auth and user context from the shell. Don't call the identity provider yourself.

Design system and shared components

- Use the design system first: \[link\].
- If you need a new component, propose it in \[channel\] before building your own.

Dependencies and bundle size

- Use libraries from the approved list. Shared libraries must use the versions pinned by the platform.
- Bundle budget per module: \[N\] KB gzipped. CI fails the build if you exceed it.

Feature flags

- Name flags \[team\]-\[feature\] and create them in \[tool\].
- Your team removes the flag within \[N\] sprints of a full rollout.

Quality gates: what CI checks

| Check | Effect |

## Releases

We release \[every N weeks / on day X\]. Code cut-off is \[day, time\]. Release notes are posted in #releases.

**Merge to main**All gates green

**Dev**Deployed automatically on merge

**Test / UAT**Release candidate cut at the code cut-off

**Production**Released by the platform team

Getting your change into a release

- Changes merged before the cut-off go into the next release. Check \[release dashboard\] to see if yours is included.
- Ship unfinished work behind a feature flag. Don't hold back a merge to wait for a release.

Hotfixes

- Only for \[Sev 1–2\] issues. Ask in #platform-help and tag \[@release-manager\].
- A platform engineer and your tech lead must both approve.

Rollback

- The platform team can roll back \[the whole app / a single module\] in about \[N\] minutes.
- The fastest fix is usually to turn the feature flag off, and your team can do that yourselves.
